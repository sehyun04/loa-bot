# gempago/vision

젬 가공 화면을 읽는 쪽. **범용 OCR 을 쓰지 않는다.**

## 왜 OCR 을 버렸나

`web/gempago-poc` 가 Tesseract 로 만든 버전이다. 실제 게임 캡처로 7라운드를 돌렸는데
매 라운드마다 **전에 없던 형태로** 깨졌다.

- `증가` -> `증카`, `중가`, `종카`, `증로`
- `▲` 아이콘 -> `"`, `속`, `A`
- 열 구분 통로에 낀 노이즈 때문에 옆 열 라벨과 병합
- 버튼 텍스트 `가공 하기 (979)` 가 가짜 옵션으로 파싱

정규식을 넓히면 가짜 옵션이 늘고, 좁히면 진짜를 놓쳤다. 신뢰도 점수로 거르는 것도
측정해보고 버렸다 — `▲`->`A` 가 87점, 오독한 `함` 이 91점, 정답 `의` 가 65점이었다.
**신뢰도와 정답률에 상관이 없다.**

근본 원인은 도구 선택이다. 이 화면의 글자는 게임이 고정 폰트로 렌더한, 종류가 정해진
문자열이다. 즉 "인식" 문제가 아니라 **"정해진 후보 중 어느 것인가" 하는 조회 문제**다.
범용 OCR 은 열린 문자 공간을 가정하므로 틀릴 때도 그럴듯한 글자를 뱉고, 틀렸다는 걸
알 방법이 없다. NCC 템플릿 매칭은 점수를 주므로 **"모르겠다"고 말할 수 있다.**

같은 결론에 도달한 선례가 있다 (`airplaner.github.io/lostark-arkgrid-gem-locator-v2`).
해당 사이트의 워커를 뜯어보면 OCR 이 없고 템플릿 매칭만 있다.

## 검증된 것

로아젬1.PNG 에서 템플릿을 뜨고 **로아젬2.PNG** 에서 판별:

- 옵션명 4/4 정답 (정답 0.996~1.000 vs 오답 0.30~0.35, 마진 0.65)
- 값 4/4 정답
- `Lv.1` vs `Lv.2` 는 문자열 전체로 매칭하면 마진이 0.063 밖에 안 나온다.
  숫자 부분만 잘라서 매칭하면 0.47~0.56 으로 회복된다.

## 알려진 한계 (fixtures 가 이걸 지킨다)

템플릿은 **문자열 x UI 컨텍스트** 단위다. 같은 `Lv.` 여도 배경이 다르면 다른 템플릿이다.
`test.js` 가 이걸 검증한다 — 선택지 행에서 뜬 `Lv.` 템플릿은

- 같은 행 배경(`cmp_row.png`)에서 **1.0000**
- 다이아 배경(`cmp_diamond.png`)에서 **0.44**

즉 배경별로 템플릿을 따로 떠야 한다. 이 수치가 흔들리면 `ncc.js` 가 깨진 것이다.

## 파일

| 파일 | 용도 |
|---|---|
| `ncc.js` | NCC 매칭. 브라우저/Node 양쪽. 의존성 없음 |
| `png.js` | PNG 디코드/인코드. **Node 전용**(zlib). 템플릿 제작·테스트용 |
| `templates/` | 확정된 템플릿 |
| `fixtures/` | 회귀 테스트 입력 |
| `scratch-assets/` | 탐색 중 잘라둔 것들. **출처와 배율이 서로 안 맞는다** |

`scratch-assets/` 는 검증 세션에서 나온 잔재다. 당시 스크립트가 원본 스크린샷에서
템플릿을 뜨고 같은 실행 안에서 매칭했기 때문에, 저장된 PNG 끼리는 배율이 맞지 않는다
(실측: 서로 매칭하면 0.14~0.18). 지우지 않고 남겨둔 건 참고용이고, **여기서 회귀
테스트를 만들 수는 없다.**

## 남은 일

1. 원본 스크린샷(`로아젬1.PNG`, `로아젬2.PNG`)에서 템플릿 추출 파이프라인을 다시 짜서
   `templates/` 를 제대로 채운다. 4/4 결과를 재현 가능한 테스트로 만든다.
2. 앵커 기반 화면 위치 잡기 + 해상도 정규화 (FHD 기준, QHD x3/4, UHD x1/2)
3. 읽은 결과를 `../solver.js` 에 물린다

## 테스트

node web/gempago/vision/test.js
