# gempago/vision

젬 가공 화면에서 "다음 항목" 4개를 읽는다. **범용 OCR 을 쓰지 않는다.**

## 왜 OCR 을 버렸나

`web/gempago-poc` 가 Tesseract 로 만든 버전이다. 실제 게임 캡처로 7라운드를 돌렸는데
매 라운드마다 **전에 없던 형태로** 깨졌다.

- `증가` -> `증카`, `중가`, `종카`, `증로`
- `▲` 아이콘 -> `"`, `속`, `A`
- 열 구분 통로에 낀 노이즈 때문에 옆 열 라벨과 병합
- 버튼 텍스트 `가공 하기 (979)` 가 가짜 옵션으로 파싱

신뢰도 점수로 거르는 것도 측정해보고 버렸다 — `▲`->`A` 가 87점, 오독한 `함` 이 91점,
정답 `의` 가 65점이었다. **신뢰도와 정답률에 상관이 없다.**

근본 원인은 도구 선택이다. 이 화면의 글자는 게임이 고정 폰트로 렌더한, 종류가 정해진
문자열이다. 즉 "인식" 문제가 아니라 **"정해진 후보 중 어느 것인가" 하는 조회 문제**다.
범용 OCR 은 열린 문자 공간을 가정하므로 틀릴 때도 그럴듯한 글자를 뱉고, 틀렸다는 걸
알 방법이 없다. NCC 는 점수를 주므로 **"모르겠다"고 말할 수 있다.**

같은 결론에 도달한 선례가 있다 (`airplaner.github.io/lostark-arkgrid-gem-locator-v2`).
해당 사이트의 워커를 뜯어보면 OCR 이 없고 템플릿 매칭만 있다.

## 어떻게 읽나

### 1. 앵커로 원점과 배율을 잡는다

절대 좌표를 쓰지 않는다. 창 위치가 바뀌면 전부 틀리기 때문이다.
**"다음 항목 중 무작위로 적용됩니다."** 한 줄을 찾고 나머지는 전부 거기서의 상대 위치다
(`layout.js` 의 `REF`). 이 문장은 가공 화면에 항상 있고 폭이 220px 이라 오탐이 없다.

전탐색은 80억 연산이라 불가능해서 1/4 축소본에서 대충 찾고 원본에서 주변만 다시 훑는다
(`ncc.locate`). 2048x1280 전체 화면 기준 130ms.

**위치만 맞추면 안 된다.** NCC 는 배율에 전혀 관대하지 않다 - 2.3% 만 달라도 앵커 점수가
**1.000 에서 0.56 으로** 떨어진다(실측: 2048x1280 을 2000x1250 으로 리샘플한 캡처).
그래서 `ncc.findScale` 로 배율을 먼저 찾고 화면 쪽을 기준 배율로 되돌린다. 템플릿마다
크기를 바꾸는 대신 화면을 되돌리면 이후 코드는 배율을 전혀 몰라도 된다.
배율 탐색은 2초쯤 걸리므로, 같은 화면을 반복해서 읽을 때는 호출부가 `scale` 을 넘겨 건너뛴다.

실제 다른 해상도로도 확인했다. 1920x1080 으로 게임이 직접 렌더한 화면에서 배율 **0.935**
(= 1920/2048 = 0.9375 에 근접)를 찾아내고 4개를 전부 맞춘다.
해상도가 바뀌면 **패널이 놓이는 자리 자체가 달라진다는 점**에 주의 - 2048x1280 은 16:10,
1920x1080 은 16:9 라 세로 위치가 크게 어긋난다. 그래서 앵커로 원점을 잡는 방식이 필요했다.

### 2. 옵션명은 통째로 매칭한다

마진이 넉넉하다 — 같은 문자열 **0.997~1.000**, 다른 문자열 **0.256~0.261**.

### 3. 값은 쪼개서 매칭한다

통째로 매칭하면 안 된다. 실측값:

| | Lv. 1 증가 | +2 증가 | +1 증가 | Lv. 2 증가 |
|---|---|---|---|---|
| **Lv. 1 증가** | 1.000 | 0.688 | 0.791 | **0.907** |
| **+2 증가** | 0.688 | 1.000 | **0.892** | 0.805 |

정답이 1.000 이어도 오답이 0.907 이면 마진이 0.09 뿐이다. 글자 대부분이 같고 숫자 한
글자만 다르니 당연하다. 이 상태로 쓰면 언제 뒤집혀도 이상하지 않다.

그래서 **접두(`Lv.` / `+`) · 숫자 · 접미(`증가`)** 로 나눠서 각각 맞춘다.

숫자는 글리프에 딱 맞추지 않고 **고정폭 8px 창**을 쓴다. 좌우 여백이 패턴에 들어가서
얇은 `1`(폭 2px)과 넓은 `2`(폭 6px)가 폭 자체로 갈린다. 마진이 **0.09 -> 0.60** 으로
회복된다 (같은 숫자 0.93~0.96, 다른 숫자 0.24~0.33).

창 위치를 글자 중심으로 계산해서 **고정하면 안 된다.** 글리프가 2~6px 라 1px 만
어긋나도 점수가 1.000 -> 0.575 로 떨어진다(실측). 접두와 접미 사이 구간에서 템플릿을
미끄러뜨리고 최고점을 고른다 — 정렬은 NCC 가 알아서 맞춘다.

값의 문법이 하나가 아니다. 실제 캡처로 확인된 형태:

| 화면 표기 | 구조 |
|---|---|
| `Lv. 3 증가` · `+4 증가` · `-1 감소` · `Lv. 1 감소` | 접두 + 숫자 + 접미 |
| `1회 증가` · `2회 증가` | 숫자 + 접미 (접두 없음) |
| `효과 변경` · `유지` · `+100% 증가` · `-100% 감소` | 숫자 없음, 통짜 |

어떤 문법으로 읽을지는 **옵션명이 결정한다** (`가공 상태` -> 유지, `가공 비용` -> ±100%,
`다른 항목 보기` -> N회). 옵션명은 마진이 0.7 이상이라 이 분기가 가장 믿을 만하다.

한 덩어리로 보이는 표기가 실제로는 두 줄로 갈린다는 점에 주의:
`가공 상태 유지` 는 옵션명 `가공 상태` + 값 `유지` 이고, 비용은 `가공 비용` + `+100% 증가` 다.
감소는 부호를 찍는다 - `-1 감소`, `-100% 감소`.

숫자 템플릿은 좌표가 아니라 **글자 덩어리 순번**으로 잘라낸다. 크롭이 1~2px 만 밀려도
좌표로 자르면 그대로 밀리는데, 숫자는 폭이 2~6px 라 그 정도로도 창이 빗나간다
(실측: 좌표로 자른 템플릿은 숫자끼리 최악 0.692 까지 붙었고, 덩어리로 자르니 0.355 로 벌어졌다).

### 4. 같은 문자열이라도 템플릿을 여러 개 둔다

리샘플된 캡처에서는 **같은 리샘플 캡처에서 자른 템플릿이 무조건 이긴다.** 화질이 아니라
출처가 점수를 가른다:

| 대상 | plus | minus | jeungga | gamso |
|---|---|---|---|---|
| 선명한 원본 (`+2 증가`) | **1.000** | 0.553 | **0.843** | 0.315 |
| 리샘플 캡처 (`+1 증가`) | 0.706 | **0.718** | 0.414 | **0.489** |

아래 줄이 전부 오답이다. `minus`/`gamso` 만 리샘플 캡처에서 잘랐기 때문에 생긴 편향이다.
그래서 같은 문자열이라도 여러 출처에서 잘라 두고(`manifest.json` 의 같은 `key`)
매칭은 그중 최고점을 쓴다. 이 하나로 40개 중 13개 오답이 0개가 됐다.

### 5. 애매하면 의심으로 표시한다

옵션명/값 각각 점수 0.8, 옵션명은 2등과의 마진 0.15 를 넘어야 `confident: true` 다.
하나라도 미달이면 그 열은 통째로 의심이다. 틀린 값을 조용히 넘기는 것보다 낫다.

의심 표시는 "틀렸다"가 아니라 "사람이 확인하라"는 뜻이다. 지금 40개 중 4개가 걸리는데
전부 `아군 피해 강화` 와 `아군 공격 강화` 처럼 한 글자만 다른 옵션명이다(마진 0.10).
넷 다 정답이었지만 임계값을 낮추면 경계가 헐거워지므로 그대로 뒀다.

## 검증 상태

`node web/gempago/vision/test.js` — **56개 통과**.
캡처 15장 x 4개 = **옵션 60개 전부 정답** (15장 처리 360ms, 배율을 알려준 경우).

정답표는 `fixtures/captures.json` 에 있다. 눈으로 읽어서 적었고, 이미지는 앵커 주변만
잘라 저장했다(원본 4.5MB 씩을 저장소에 넣지 않기 위해).

캡처 15장이 커버하는 것:

- 젬 계열: 혼돈(침식), 질서(견고·안정)
- 효과 이름 7종: 공격력 · 보스 피해 · 추가 피해 · 아군 공격 강화 · 아군 피해 강화 등
- 숫자 1~4 (증감폭 최대가 +4 라 5 는 옵션에 안 뜬다)
- `증가` / `감소` — 수치(`-1 감소`)와 효과(`Lv. 1 감소`) 양쪽
- `효과 변경` · `유지` · `+100% 증가` · `-100% 감소` · `1회 증가` · `2회 증가`
- 배율 3종: 1.0 (2048x1280), 0.98 (리샘플), **0.935 (1920x1080 네이티브)**

### 아직 없는 것

- **효과 이름**이 게임 전체로는 훨씬 많다. 아틀라스에 없는 이름은 읽지 못하고 거부한다.
  이건 근본적으로 캡처를 계속 모아야 하는 부분이다.
- 2560x1440, 3840x2160 같은 더 큰 해상도. 지금 검증된 배율은 0.935 ~ 1.0 구간뿐이다.
## 게임 밝기 설정은 신경 쓸 필요 없다

다른 도구들은 "게임 밝기를 70 이상으로 맞춰라" 같은 조건을 요구하기도 한다.
여기서는 필요 없다. NCC 가 평균을 빼고 표준편차로 나누기 때문에 **선형 밝기/대비
변화에는 원리상 완전히 무관**하고, 실제로 그렇다(`test.js` 의 "밝기/대비 불변" = 1.0000).

게임 밝기 설정은 보통 감마(비선형)라 원리만으로는 안 되고 재봐야 한다. 재봤다:

| 변형 | 옵션 60개 정답 |
|---|---|
| 원본 | 60/60 |
| 감마 0.5 / 0.7 / 1.4 / 2.0 | 60/60 |
| 대비 x0.5 | 60/60 |
| 대비 x1.8 -40 | 60/60 |
| 어둡고 밋밋하게 (x0.35 +140) | 60/60 |

**정말로 깨지는 건 포화뿐이다.** 밝기를 올려서 글자가 흰색으로 날아가면 정보 자체가
사라지므로 어떤 방법으로도 복구할 수 없다. 한계는 이렇다:

| 포화 픽셀 비율 | 옵션 60개 정답 |
|---|---|
| ~4.5% | 60/60 |
| 6.3% | 44/60 |
| 9.5% | 16/60 |

4.5% 포화를 만들려면 8비트 기준 밝기를 +130 올려야 한다. 정상적인 게임 설정으로는
근처도 못 간다. 즉 **화면이 하얗게 타 보이지만 않으면 된다.**

## JPG 로 줘도 된다

캡처를 PNG 가 아니라 JPG 로 받아도 되는지 재봤다. JPEG 는 8x8 DCT 블록 단위로 뭉개고
색차를 절반으로 줄이므로(4:2:0), 글자 가장자리에 링잉이 생긴다. 글자가 2~6px 인
숫자 창에는 위험해 보인다. 실제로는 아니었다.

15장을 품질별로 JPEG 인코딩했다가 되돌려서 그대로 읽혔다(subsampling 4:2:0).

| 품질 | 옵션 60개 정답 | 의심 표시 |
|---|---|---|
| 원본 PNG | 60/60 | 5 |
| q95 ~ q40 | 60/60 | 5 |
| q30 / q20 | 60/60 | 9 |
| q10 | 60/60 | 10 |
| q5 | 57/60 | 36 |

배율 탐색도 멀쩡하다. q40 에서 앵커 점수가 1.000 -> 0.983 (2048 네이티브),
0.937 -> 0.921 (0.98 리샘플), 0.735 -> 0.728 (1920 네이티브) 로 내려갈 뿐이고
셋 다 배율은 정확히 맞힌다.

**q10 까지 무손실과 차이가 없다.** 어떤 도구도 q10 으로 저장하지 않으므로 실무적으로는
JPG 여부를 신경 쓸 필요가 없다. q5 에서 처음 깨지는데, 틀리는 방식이 `-1 감소` ->
`효과 변경` 처럼 값 전체를 놓치는 쪽이라 의심 표시가 5 -> 36 으로 먼저 튄다.
즉 깨질 때는 조용히 틀리지 않는다.

주의할 것은 압축이 아니라 **크기 변경**이다. 캡처를 축소해서 보내면 배율과 템플릿
출처가 같이 달라지므로(위 4번 항목) 그쪽이 훨씬 위험하다.

## 다이아 (현재 수치) - 이름은 되고 숫자는 표본이 모자란다

젬의 현재 수치를 보여주는 다이아 4개의 기하 구조는 확정했다(`layout.diamonds`).
앵커에서의 상대 위치로 8개 띠(라벨 4 + 값 4)를 정확히 집어내고, 캡처 15장 전부에서
띠 안에 글자가 들어 있는 것을 `test.js` 가 확인한다. 해상도가 달라도(1920x1080) 맞는다.

### 앞서 적었던 결론 두 개는 틀렸다

전에 "통짜 매칭 마진이 음수", "좌우 템플릿은 서로 못 쓴다(0.299)" 라고 적어 뒀었다.
둘 다 **템플릿을 띠와 같은 폭으로 떠서 미끄러질 자리를 안 준 것**이 원인이었다.
위 3번 항목(숫자 창을 중심 계산으로 고정하면 안 된다)과 같은 실수다.
템플릿을 좌우 8px 좁게 뜨고 대상 띠 안에서 미끄러뜨리면:

| | 점수 |
|---|---|
| `추가 피해` 좌 -> 좌 | 1.000 |
| `추가 피해` 좌 -> **우** | 0.892 (다른 이름 0.362) |
| `아군 공격 강화` 좌 -> **우** | 0.909 (다른 이름 0.792) |

**옵션명은 좌우 자리를 가리지 않는다.** 30개 표본(15장 x 좌우) leave-one-out 으로
**30/30**, 최소 마진 0.016. 반대편 자리 템플릿밖에 없던 2건도 다 맞았다.
따라서 (이름 x 자리) 조합마다 템플릿을 따로 뜰 필요가 없다.

마진이 얇은 것은 `아군 공격 강화` / `아군 피해 강화` 처럼 한 글자만 다른 쌍인데,
이건 옵션 행에서도 똑같이 얇다(0.10). 다이아 고유의 문제가 아니다.

### 숫자는 배경을 빼야 한다

값 띠는 160px 인데 글자는 3~12px 라 **배경이 점수를 거의 다 먹는다.** 통짜로 비교하면
어떤 후보든 0.98 이 나오고 최소 마진이 **0.005** 다. 띠를 좁혀도(반폭 80 -> 24) 마진은
0.021 까지밖에 안 오르고, 더 좁히면 좌/우는 `Lv. N` 이라 숫자가 아니라 `Lv.` 를 자른다.

배경은 캡처마다 **완전히 동일한 UI 아트**라서 빼버릴 수 있다. 다만 방법을 가린다:

| 방법 | 결과 |
|---|---|
| 픽셀별 최소값을 배경으로 | 53/60. 캡처마다 밝기가 달라서 **제일 어두운 캡처가 통째로 배경판이 되고** 그 캡처 잔차가 0 이 된다 |
| 최소값 배경 + 글자 잘라내기 | 42/60. 위 문제가 그대로 증폭된다 |
| **띠를 z 정규화한 뒤 픽셀별 중앙값을 배경으로** | **55/60**, 마진 0.005 -> 0.011 |

z 정규화가 핵심이다 - 먼저 밝기를 없애야 배경판이 캡처 하나에 끌려가지 않는다.
중앙값이 여기서 통하는 이유는 값이 1~5 로 흩어져 있어서다. 옵션명 띠에서 중앙값이
실패했던 건(같은 이름 0.040) `아군 피해 강화` 가 15장 중 13장이라 중앙값에 글자가
섞였기 때문이고, 숫자 띠는 그 조건이 아니다.

### 숫자 템플릿은 네 자리가 공유한다 - 자리별로 모을 필요가 없다

배경을 빼고 나면 잔차에는 **글자만** 남는다. 글자는 자리가 달라도 같은 폰트다.
따라서 "왼쪽 다이아의 2", "아래 다이아의 3" 을 따로 모을 이유가 없다.
이게 중요한 이유는 젬을 굴려 특정 수치를 만드는 데 **골드가 들기 때문**이다.
캡처를 요구할 때 이 비용을 먼저 따져야 한다.

단, 잔차 띠를 통째로 비교하면 안 된다. 좌/우는 `Lv. N` 이라 잔차에 `Lv.` 이 같이
남고 위/아래는 숫자뿐이라, 띠끼리 대면 앞글자가 어긋난다. **숫자 덩어리만 떼어낸 뒤**
공유해야 한다(배경이 없으니 이제 덩어리 찾기가 안정적이다).

| 방식 | 정답 | 최소 마진 |
|---|---|---|
| 같은 자리 템플릿만, 띠 통째로 | 55/60 | 0.011 |
| 네 자리 공유, 띠 통째로 | 55/60 | 0.029 |
| **네 자리 공유, 숫자만 떼어서** | **56/60** | **0.026** |

### 남은 오답은 표본이 아니라 해상도다

56/60 의 오답 4개 중 **3개가 1920x1080 네이티브 한 장(cap26)** 이다.
그 캡처를 빼면 **55/56**, 유일한 오답은 cap25 위쪽 하나다.

배율 분포가 이렇다: 2048 원본 2장, 0.98 리샘플 12장, **1920 네이티브 1장**.
1920 은 한 장뿐이라 비교할 같은 출처 템플릿이 없다. 위 4번(템플릿 출처 편향)에서
이미 확인한 것과 같은 이야기다.

### 그래서 필요한 캡처

**특정 젬 상태를 만들 필요가 없다.** 숫자 1~5 는 자리를 합치면 이미 다 모였고
(1이 29회, 2가 5, 3이 5, 4가 8, 5가 13), 템플릿은 자리끼리 공유된다.

필요한 건 **1920x1080 에서 평소대로 찍은 가공 화면 몇 장**뿐이다. 어떤 젬이든,
어떤 수치든 상관없다. 골드가 들지 않는다.

검산에 쓸 수 있는 성질도 확인해 뒀다: `젬 포인트` 숫자가 **네 수치의 합과 정확히
일치한다**(캡처 15장 전부). 네 자리를 각각 읽은 뒤 합이 안 맞으면 어딘가 틀렸다는
뜻이므로, 자신 없는 자리를 골라내는 데 쓸 수 있다.

## 파일

| 파일 | 용도 |
|---|---|
| `ncc.js` | NCC 매칭, 축소 탐색, 배율 탐색. 브라우저/Node 공용, 의존성 없음 |
| `layout.js` | 앵커 기준 기하 구조 + 배율 정규화. 글자 덩어리 분할 |
| `reader.js` | 4개 항목 읽기. 옵션명 계열에 따라 값 문법을 갈라 읽는다 |
| `interpret.js` | 읽은 글자 <-> `rules.js` 항목 id. 이미지를 안 만져서 캡처 없이 검증된다 |
| `atlas.js` | 템플릿 로더 (Node 전용) |
| `png.js` | PNG 디코드/인코드. **Node 전용**(zlib) |
| `templates/` | 아틀라스 + `manifest.json` (문자열·출처·계열·띄어쓰기 규칙) |
| `fixtures/` | 캡처 10장 + 정답표 `captures.json` |
| `scratch-assets/` | 탐색 중 잘라둔 것들. **출처와 배율이 서로 안 맞는다** |

템플릿 파일명이 ASCII 인 이유는 한글 파일명의 NFC/NFD 정규화가 플랫폼마다 달라서
체크아웃 후 경로가 안 맞는 일이 생기기 때문이다. 실제 문자열은 `manifest.json` 에 있다.

`scratch-assets/` 는 초기 검증 세션의 잔재다. 저장된 PNG 끼리 배율이 맞지 않아
(실측: 서로 0.14~0.18) 여기서 회귀 테스트를 만들 수 없다. 참고용으로만 남겼다.
