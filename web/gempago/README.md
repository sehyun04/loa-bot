# 젬파고

로스트아크 젬 가공 화면에서 **지금 뜬 4개로 굴릴지, 리롤할지** 알려주는 계산기.

디스코드 봇(`run/`)과는 완전히 분리돼 있다. 빌드 단계 없는 정적 페이지다.

## 실행

`fetch` 와 Web Worker 를 쓰므로 `file://` 로 열면 안 되고 로컬 서버가 필요하다.

```
cd web
python -m http.server 8777
```

`http://127.0.0.1:8777/gempago/`

## 테스트

```
node web/gempago/test.js          # 확률 표 + 솔버 (26)
node web/gempago/vision/test.js   # 화면 인식 (56)
```

## 어떻게 계산하나

몬테카를로가 아니라 **역방향 귀납법으로 정확한 값**을 구한다. 상태 공간이
`5^4 x 3 = 1875` 밖에 안 돼서 가능하다.

확률 표(`rules.js`)는 스마일게이트 공식 확률 공개 페이지 값이다. 27개 항목, 합계
정확히 100.0000%. **추정치가 아니므로 숫자를 임의로 바꾸면 결과 전체가 거짓이 된다.**

가공 1회 = 등장 가능한 항목에서 가중치 기반 **비복원**으로 4개를 뽑아 보여주고,
그중 하나가 각 25% 로 적용된다. 항목의 단위는 (수치 x 증감폭)이라 "포인트 +1" 과
"포인트 +2" 가 같이 뜨는 건 정상이다 — 실제로 같은 수치가 중복 등장하는 조합이
전체의 52% 라서, 이걸 "수치 단위 비복원"으로 잘못 모델링하면 결과가 크게 틀어진다.

### 조기 종료

화면에 **가공 완료** 버튼이 있어서 남은 횟수가 있어도 언제든 확정할 수 있다.
따라서 목표를 만족한 순간 값은 1 이고 더 굴리지 않는다. 이걸 빼먹으면 목표를 맞춘
뒤에도 -1 위험을 계속 지는 셈이라 모든 확률이 과소평가된다
(영웅 신품 `1번 효과 Lv.4` 기준 45.78% -> **48.64%**).

### 리롤 판단

```
V(s, n, r) = E_S[ max( 지금 뜬 4개로 굴리기, 리롤하고 다시 보기 ) ]
```

리롤은 가공 횟수를 안 쓰고 리롤 횟수만 줄이므로 재귀가 반드시 끝난다.

**목표가 바뀌면 판단이 저절로 바뀐다.** 휴리스틱은 없다. 같은 젬, 같은 화면인데:

> 의지력 5 / 포인트 4 / 1번 1 / 2번 1, 가공 4회 · 리롤 2회 남음
> 화면: `포인트 +1`, `가공 비용 +100%`, `가공 비용 -100%`, `가공 상태 유지`

| 목표 | 굴리기 | 리롤 | 판단 |
|---|---|---|---|
| 의지력/포인트 5/5 | 61.96% | 51.83% | **굴린다** |
| 전부 5/5/5/5 | 0.240% | 0.243% | 거의 동률 (리롤이 0.003%p 앞섬) |

안전 목표는 `포인트 +1` 하나로 끝나니까 바로 굴리고, 고점 목표는 1번/2번을 4회 안에
1 -> 5 로 올려야 해서 이 판 자체가 거의 버리는 판이다. `test.js` 가 이걸 고정한다.

## 구조

| 파일 | 역할 |
|---|---|
| `rules.js` | 공식 확률 표. 등장 조건. **Node/브라우저 공용** |
| `solver.js` | DP. `solveNoReroll`, `solveFull`, `decide` |
| `worker.js` | 솔버를 워커에서 돌린다. 영웅 기준 목표당 약 2초 |
| `app.js` | 입력 UI. 여기서는 확률을 계산하지 않는다 |
| `vision/` | 화면 인식 (NCC 템플릿 매칭). `vision/README.md` 참고 |
| `vision/interpret.js` | 읽은 글자 <-> 확률 표 항목 id 변환. 이미지를 안 만져서 캡처 없이 검증된다 |
| `vision/atlas-browser.js` | 브라우저용 템플릿 로더. `atlas.js` 는 fs 를 쓰는 Node 전용이다 |

## 항목 표기

UI 는 항목을 게임 화면 그대로 보여준다 - `1번 효과 +1` 이 아니라 `공격력 Lv. 1 증가`.
화면과 목록을 눈으로 대조해야 하는 작업이라 표기가 다르면 그 자체가 실수의 원인이 된다.
1번/2번 효과 이름은 젬마다 다르므로 사용자가 입력한다(`vision/interpret.js` 의 `toScreenText`).

같은 변환의 반대 방향(`toOutcomeId`)이 화면 인식 결과를 솔버 입력으로 바꾼다.
27개 항목 전부 왕복 검증되어 있다.

`worker.js` 가 `importScripts` 대신 자체 CommonJS 로더를 쓰는 이유는 거기 주석에 있다
(전역 스코프 공유 때문에 `MIN_VALUE` 등이 재선언 에러를 낸다).

## 화면 인식

`vision/` 이 가공 화면에서 "다음 항목" 4개를 읽는다. 실제 캡처 15장 x 4개 =
**옵션 60개 전부 정답**이고 (해상도 2048x1280 / 1920x1080 둘 다), 읽은 결과는
`vision/interpret.js` 가 확률 표의 항목 id 로 바꿔 그대로 솔버에 넣는다.
자세한 내용과 **아직 없는 것**은 [vision/README.md](vision/README.md) 참고.

UI 에서 쓰는 방법은 두 가지다.

- **화면 공유** - `getDisplayMedia` 로 게임 화면을 받아 "지금 읽기" 를 누르거나
  "계속 읽기" 로 1.5초마다 자동으로 읽는다. 30fps 로 받을 이유가 없다. 가공은 사람이
  버튼을 눌러야 진행되고 인식은 100ms 안쪽이라, 프레임을 쏟아부어봐야 낭비다.
- **PNG 끌어다 놓기** - 캡처 파일을 창에 던지면 읽는다. 공유가 안 될 때 확인용으로도 쓴다.

배율 탐색이 2초쯤 걸리므로 워커가 한 번 찾은 배율을 캐시한다. 창 크기가 바뀌면
(공유를 다시 시작하거나 다른 파일을 놓으면) 캐시를 비우고 다시 찾는다.

읽은 옵션명 중 이 젬의 수치로 매칭되지 않는 것은 효과 이름이다. 비어 있는
"1번/2번 효과 이름" 칸에 자동으로 채운다. **어느 쪽이 1번인지는 옵션 목록만으로는
알 수 없으므로** 채웠다는 사실을 알리고 사용자가 바꿀 수 있게 둔다.

화면에는 보이는데 지금 입력한 수치에서는 나올 수 없는 항목이면(예: 그 수치가 4 인데
`+4 증가` 가 보임) 조용히 넘기지 않고 어긋났다고 알린다.

## 남은 일

- 다이아 4개(현재 수치)도 읽기. 배경이 달라 템플릿을 따로 떠야 한다.
  그러면 수치를 손으로 넣을 필요가 없어진다
- 효과 이름 캡처를 계속 모아 아틀라스 채우기 (없는 이름은 읽지 못하고 거부한다)
- `MAX_REROLL = 6` 은 절단이다. 7·8과 비교해서 오차가 무시 가능한지 미확인
- 골드 비용을 고려한 판단 (지금은 확률만 본다)
