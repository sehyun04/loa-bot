# 젬파고

로스트아크 젬 가공 화면에서 **지금 뜬 4개로 굴릴지, 리롤할지** 알려주는 계산기.

디스코드 봇(`run/`)과는 완전히 분리돼 있다. 빌드 단계 없는 정적 페이지다.

화면을 공유하면 **목표를 뺀 모든 입력이 자동으로 채워진다.** 사람이 하는 일은
목표를 고르는 것과, 인식이 흔들렸을 때 그 칸만 고치는 것뿐이다.

## 실행

`fetch` 와 Web Worker 를 쓰므로 `file://` 로 열면 안 되고 로컬 서버가 필요하다.

```
cd web/gempago
python -m http.server 8080
```

`http://localhost:8080`

`cd web` 에서 띄우고 `/gempago/` 로 들어가도 된다. 상대 경로만 쓴다.

## 테스트

```
node web/gempago/test.js          # 확률 표 + 솔버 (26)
node web/gempago/vision/test.js   # 화면 인식 (109, 실제 캡처 49장 포함, 1분쯤 걸린다)
```

## 어떻게 계산하나

몬테카를로가 아니라 **역방향 귀납법으로 정확한 값**을 구한다. 상태 공간이
`5^4 x 3 = 1875` 밖에 안 돼서 가능하다.

확률 표(`rules.js`)는 스마일게이트 공식 확률 공개 페이지 값이다. 27개 항목, 합계
정확히 100.0000%. **추정치가 아니므로 숫자를 임의로 바꾸면 결과 전체가 거짓이 된다.**

가공 1회 = 등장 가능한 항목에서 가중치 기반 **비복원**으로 4개를 뽑아 보여주고,
그중 하나가 각 25% 로 적용된다. 항목의 단위는 (수치 x 증감폭)이라 "포인트 +1" 과
"포인트 +2" 가 같이 뜨는 건 정상이다 - 실제로 같은 수치가 중복 등장하는 조합이
전체의 52% 라서, 이걸 "수치 단위 비복원"으로 잘못 모델링하면 결과가 크게 틀어진다.

### 조기 종료

화면에 **가공 완료** 버튼이 있어서 남은 횟수가 있어도 언제든 확정할 수 있다.
따라서 목표를 만족한 순간 값은 1 이고 더 굴리지 않는다. 이걸 빼먹으면 목표를 맞춘
뒤에도 -1 위험을 계속 지는 셈이라 모든 확률이 과소평가된다
(영웅 신품 `1번 효과 Lv.4` 기준 45.78% -> **48.64%**).

### 리롤 판단

```
V(s, n, r) = E_S[ max( 지금 뜬 4개로 굴리기, 리롤하고 다시 보기 ) ]
```

리롤은 가공 횟수를 안 쓰고 리롤 횟수만 줄이므로 재귀가 반드시 끝난다.

**목표가 바뀌면 판단이 저절로 바뀐다.** 휴리스틱은 없다. 같은 젬, 같은 화면인데:

> 의지력 5 / 포인트 4 / 1번 1 / 2번 1, 가공 4회 · 리롤 2회 남음
> 화면: `포인트 +1`, `가공 비용 +100%`, `가공 비용 -100%`, `가공 상태 유지`

| 목표 | 굴리기 | 리롤 | 판단 |
|---|---|---|---|
| 의지력/포인트 5/5 | 61.96% | 51.83% | **굴린다** |
| 전부 5/5/5/5 | 0.240% | 0.243% | 거의 동률 (리롤이 0.003%p 앞섬) |

안전 목표는 `포인트 +1` 하나로 끝나니까 바로 굴리고, 고점 목표는 1번/2번을 4회 안에
1 -> 5 로 올려야 해서 이 판 자체가 거의 버리는 판이다. `test.js` 가 이걸 고정한다.

## 구조

| 파일 | 역할 |
|---|---|
| `rules.js` | 공식 확률 표. 등장 조건. **Node/브라우저 공용** |
| `solver.js` | DP. `solveNoReroll`, `solveFull`, `decide` |
| `worker.js` | 솔버와 화면 인식을 워커에서 돌린다. 영웅 기준 목표당 약 2초 |
| `app.js` | UI 전부. **여기서는 확률을 계산하지 않는다** |
| `index.html` | 화면 구조와 **사용자에게 보이는 문구** |
| `style.css` | 보석 테마. 이모지 없이 SVG·도형·색만 쓴다 |
| `vision/` | 화면 인식. `vision/README.md` 에 전부 적혀 있다 |
| `vision/interpret.js` | 읽은 글자 <-> 확률 표 항목 id 변환. 이미지를 안 만져서 캡처 없이 검증된다 |
| `vision/atlas-browser.js` | 브라우저용 템플릿 로더. `atlas.js` 는 fs 를 쓰는 Node 전용이다 |

## 항목 표기

UI 는 항목을 게임 화면 그대로 보여준다 - `1번 효과 +1` 이 아니라 `공격력 Lv. 1 증가`.
화면과 목록을 눈으로 대조해야 하는 작업이라 표기가 다르면 그 자체가 실수의 원인이 된다.
1번/2번 효과 이름은 젬마다 다르므로 화면에서 읽어 채운다(`vision/interpret.js` 의
`toScreenText`).

같은 변환의 반대 방향(`toOutcomeId`)이 화면 인식 결과를 솔버 입력으로 바꾼다.
27개 항목 전부 왕복 검증되어 있다.

`worker.js` 가 `importScripts` 대신 자체 CommonJS 로더를 쓰는 이유는 거기 주석에 있다
(전역 스코프 공유 때문에 `MIN_VALUE` 등이 재선언 에러를 낸다).

## 화면 인식

`vision/` 이 가공 화면에서 이만큼을 읽는다.

| 읽는 것 | 채우는 입력 |
|---|---|
| "다음 항목" 4개 | 랜덤 항목 4개 드롭다운 |
| 다이아 4개 (현재 수치 + 효과 이름) | 의지력/포인트/1번/2번, 젬 계열, 효과 이름 칸 |
| 리롤 횟수 | 남은 리롤 |
| 가공 횟수 `(N/M)` | 남은 가공, 그리고 M 이 등급을 알려준다 |
| 가공 비용 금액 | 가공 비용 배율 (`0 / 900 / 1800` 골드 -> `-1 / 0 / +1`) |
| 젬 포인트 | **검산용.** 네 수치의 합과 대조한다 |

실제 캡처 **49장**(2048x1280 4장, 배율 0.98 12장, 1920x1080 33장)으로 회귀 테스트를
돌린다. 자세한 내용과 **아직 없는 것**은 [vision/README.md](vision/README.md) 참고.

### 젬 포인트 검산

젬 포인트 = 네 수치의 합이다. 그래서 다이아 한 자리가 애매해도 나머지 셋과 합으로
**복구**할 수 있고, 합이 안 맞으면 **네 자리 전부 의심으로 내린다**. 인식이 조용히
틀리는 것을 막는 마지막 방어선이다(`reader.reconcileGem`).

### 배율

앵커("다음 항목 중 무작위로 적용됩니다.")를 찾아 원점과 배율을 동시에 잡는다.
탐색이 1초쯤 걸리므로 워커가 한 번 찾은 배율을 캐시한다. 공유를 다시 시작하거나
다른 파일을 놓으면 캐시를 비운다.

```
배율 탐색 포함   1000~1100ms   (공유 켜고 첫 1회)
배율 아는 뒤       55~70ms     (그 다음부터 계속)
```

**이 60ms 가 UI 설계를 정했다.** 사람이 "읽기" 버튼을 누를 이유가 없어서
공유를 켜면 0.7초마다 알아서 읽는다.

## UI

### 배치

매 턴 보는 것은 판정 하나뿐이고 나머지는 전부 자동으로 채워지거나 세션당 한 번
정한다. 가운데가 답이고, 양옆이 그 답을 정하는 두 입력이다 - 왼쪽은 화면에서 읽어
온 것, 오른쪽은 사람이 정하는 것.

```
+---------------------- 화면 공유 / 상태 -----------------------+
+- 왼쪽 (4) -------+- 가운데 (5) --------------+- 오른쪽 (4) ---+
| 읽은 젬  (접힘)  | 랜덤 항목 4개  (접힘)     | 목표           |
| 읽기 상세(접힘)  | 답 (판정 + 확률 2개)      |                |
+------------------+---------------------------+----------------+
```

1100px 아래에서는 2단이 되고 **가운데가 맨 위 전체 폭**으로 올라온다.
700px 아래에서는 한 줄이 된다. 좁아질수록 답이 먼저다.

### 접어 두되 조용히 틀리지 않는다

젬 상태 11칸과 항목 4개는 전부 자동이라 평소에는 `<details>` 로 접혀 있다.
다만 **접힌 채로도 무엇이 들어갔는지 한 줄 요약을 보여준다.** 안 보이면 잘못 읽은
값으로 계산된 답을 그대로 믿게 된다.

인식이 흔들린 패널만 테두리가 노랑(`attention`) / 빨강(`bad`)으로 바뀌고
**문제가 새로 생긴 순간에만** 펼쳐진다(`markFold`). 매번 펼치면 자동 갱신이 도는
동안 사용자가 접어도 계속 다시 열려서 못 쓴다.

### 화면이 바뀌었을 때만 반영한다

자동 갱신이 0.7초마다 도는데 매 틱 입력칸을 덮어쓰면 사람이 손으로 고친 값이 바로
뭉개진다. 인식이 애매해서 사람이 고쳐 넣는 상황이 정확히 그때라, 하필 제일 필요할 때
못 쓰게 된다. 그래서 판독 결과의 **지문**(`readingKey`: 다이아 4개 + 메타 + 옵션 4개)을
비교해 달라졌을 때만 반영한다. "한 번 읽기" 버튼은 지문을 무시하고 강제로 다시 넣는다.

### 문구는 index.html 이 주인이다

사용자에게 보이는 문구는 `index.html` 에 있고 `app.js` 는 그걸 읽어다 쓴다
(`IDLE_LIVE = $('liveState').textContent`). 같은 문장을 두 파일에 두면 한쪽만
고쳐진다. **`app.js` 에 안내 문구를 하드코딩하지 말 것.**

같은 이유로 `app.js` 는 요약 span 이 없어도 굴러가야 한다(`renderPickSummary` 의
널 가드). HTML 은 앞으로도 계속 고칠 것이다.

### 상태 표시 규칙

- 잘 읽히는 중에는 "읽기 상세" 요약줄이 **비어 있다.** 읽은 내용은 이미 "읽은 젬" /
  "랜덤 항목 4개" 요약에 있다. 요약줄은 문제가 있을 때만 쓴다.
- "템플릿을 불러오는 중" 같은 내부 사정은 안 띄운다. 사용자가 할 수 있는 게 없다.
  실패했을 때만 말한다.
- "계산 중" 스피너는 **150ms 뒤에야** 뜬다. 목표당 첫 풀이만 2초고 그 뒤는 캐시라
  즉시 끝나는데, 자동 갱신 중에 매번 깜빡이면 답보다 스피너가 눈에 띈다.
- 이모지는 쓰지 않는다. 스피너도 CSS 테두리 한 조각을 돌린 것이다.

### 보석 테마

강조색이 **젬 계열을 따라간다** - 질서는 빨강, 혼돈은 파랑. 화면에 띄운 젬과
같은 색이어야 헷갈리지 않는다. `app.js` 가 `body[data-gem]` 을 바꾸면 로고 SVG,
다이아 마커, 추천 카드, 프리셋 버튼, 포커스 링이 전부 같이 갈린다.

이모지를 안 쓰고 보석 표시를 내는 방법 두 가지: 머리말 로고는 브릴리언트 컷 SVG
(CSS 변수를 물고 있어 색이 따라온다), 접이식 제목 앞은 45도 돌린 사각형이다.

**빛나는 건 답 패널 하나뿐이다.** 장식이 판정을 가리면 안 된다.

`select` 에는 `background` 단축 대신 `background-color` 와 `background-image` 를
따로 준다. 단축을 쓰면 `background-color` 가 `transparent` 로 돌아가는데, 네이티브
드롭다운 목록이 그 색으로 그려져서 **펼쳤을 때 글씨가 안 보인다.**

### 어긋남 감지

화면에는 보이는데 지금 입력한 수치에서는 나올 수 없는 항목이면(예: 그 수치가 4 인데
`+4 증가` 가 보임) 조용히 넘기지 않고 어긋났다고 알린다.
