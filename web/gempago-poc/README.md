# 젬 툴팁 화면 인식 POC

로스트아크 젬 툴팁을 **화면 공유 -> OCR -> 정규식 파싱** 으로 읽어내는 부분만 떼어낸 실험용 정적 웹페이지다.
loatto.kr 의 젬파고가 하는 "화면 공유로 게임 창을 가리키면 지금 마우스가 올라간 젬의 옵션을 알아서 읽어온다"
는 동작 중, **화면 인식 단계만** 구현했다.

젬 가공 확률 시뮬레이터는 **범위 밖**이다. loatto 의 시뮬레이션 규칙/확률표를 모르기 때문에 추측해서 만들지 않았다.

이 폴더는 봇 코드(`run/`)와 완전히 무관하다. 아무것도 import 하지 않고, 봇 동작에도 영향을 주지 않는다.

## 구성

| 파일 | 역할 |
| --- | --- |
| `index.html` | 화면 구조 |
| `style.css` | 다크 테마 |
| `app.js` | 캡처, 선택 영역, 전처리, OCR 호출, 파서 (파서는 Node 에서도 `require` 가능) |
| `test-fixtures/` | 실제 화면에서 나온 OCR 결과 + 회귀 테스트 러너 |

빌드 단계 없음. 번들러 없음. Tesseract.js 만 CDN 에서 불러온다.

## 실행

```bash
cd web/gempago-poc
python -m http.server 8000
```

또는

```bash
cd web/gempago-poc
npx serve
```

브라우저에서 `http://localhost:8000` 접속.

> `index.html` 을 더블클릭해서 `file://` 로 여는 방식은 **동작하지 않는다.**
> `getDisplayMedia` 는 보안 컨텍스트(https 또는 localhost)에서만 쓸 수 있다.
> 반드시 위처럼 로컬 서버를 띄워서 열어야 한다.

## 사용법

1. **화면 공유 시작** 을 누르고, 브라우저가 띄우는 목록에서 로스트아크 창을 고른다.
   - 게임이 전체 화면(독점)이면 공유 목록에 안 잡히거나 검게 나올 수 있다. **테두리 없는 창 모드**를 권장한다.
2. 미리보기 위의 파란 사각형을 읽고 싶은 영역에 맞춘다.
   - 안쪽을 끌면 이동, 8개 점을 끌면 크기 조절, 빈 곳을 끌면 새로 그린다.
   - **가공 화면이라면 `다음 항목 중 무작위로 적용됩니다` 문구부터 그 아래 4열까지만 감싼다.**
     상단 원형 장식 배경은 글씨가 거의 안 읽히고, 그 잡음에서 가짜 항목이 만들어진다.
     영역 게이트가 대부분 걸러주지만, 애초에 안 넣는 것이 제일 확실하다.
   - 툴팁 크기는 게임 해상도/UI 배율에 따라 다르므로 위치 자동 검출은 하지 않는다(범위 밖).
3. 오른쪽 **OCR 입력 이미지** 미리보기를 보면서 전처리 값을 조절한다. 글씨가 또렷할수록 인식률이 오른다.
4. **지금 인식** 을 누른다. (원하면 *2초마다 자동 인식* 체크)
5. 아래에 **원본 OCR 텍스트** 와 **파싱 결과** 가 나온다.
   원본 텍스트 칸은 직접 고칠 수 있고, 고치면 파싱 결과가 즉시 다시 계산된다. 파서 튜닝할 때 편하다.

## 전처리 옵션

Tesseract 는 **밝은 배경 + 어두운 글씨** 에서 가장 잘 동작한다. 게임 툴팁은 그 반대라서 기본값이 이렇다.

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| 확대 배율 | **3.0x** | 아래 측정 결과 참고. 2.0x 는 오독이 잦다. |
| 인식 모드(PSM) | 6 (단일 블록) | 측정상 4(단일 컬럼)와 거의 같다. 잘 안 되면 바꿔볼 것. |
| 자동 대비 보정 | 켬 | 밝기 히스토그램 양끝 2% 를 잘라내고 0..255 로 늘린다. |
| 밝기 반전 | **켬** | 어두운 배경 + 밝은 글씨를 뒤집는다. |
| 이진화 임계값 | 끔 | 측정상 켜면 오히려 나빠진다. 배경이 아주 지저분할 때만. |

### 확대 배율이 가장 중요하다 (측정 결과)

실제 가공 화면을 흉내낸 이미지로 **PSM 4종 x 배율 3종 x 이진화 4종 = 48조합**을 전부 돌려
"정답 문자열 7개 중 몇 개를 살렸는지" 로 점수를 매겼다.

| 배율 | 7/7 달성 조합 | 평균 점수 | `Lv.` 를 살린 조합 |
| --- | --- | --- | --- |
| 2.0x | 1 / 16 | 4.06 | **8 / 16** |
| 3.0x | 6 / 16 | 5.88 | **16 / 16** |
| 4.0x | 3 / 16 | 5.81 | 16 / 16 |

실제 화면에서 `공격력 Lv. 1 증가` 가 `공격력 1. 1 증카` 로 나온 사고가 있었다.
`Lv.` 의 `L` 이 숫자 `1` 로 통째로 바뀐 것이라 **정규식으로는 원천적으로 복구할 수 없다.**
위 표가 그 원인을 보여준다. 2.0x 에서는 절반의 조합에서 `Lv.` 가 깨지지만
3.0x 부터는 전 조합에서 살아남는다. 그래서 기본값을 3.0x 로 올렸다.

PSM 은 생각보다 영향이 작았다(단일 블록 5.33 / 단일 컬럼 5.50 / 자동 5.08 / 흩어진 텍스트 5.08).
흩어진 텍스트(SPARSE_TEXT)가 이 화면에 더 맞을 것 같지만 실제로는 그렇지 않았고
평균 신뢰도도 가장 낮았다. 그래도 화면마다 다를 수 있어 UI 에서 고를 수 있게 해뒀다.

이진화는 끄는 쪽(평균 5.75)이 켜는 쪽(160: 4.92, 190: 4.58)보다 나았다.

### 신뢰도(confidence)로 잡음을 거르는 방법은 쓸 수 없다

"낮은 신뢰도 단어를 버리면 잡음이 사라지지 않을까" 를 실제로 측정해봤는데 **작동하지 않는다.**

| 단어 | 실제 정체 | 신뢰도 |
| --- | --- | --- |
| `A` | 장식 화살표(▲) 오독 | **87** |
| `함` | `항목` 의 오독 | **91** |
| `초` | 장식 화살표 오독 | 68 |
| `의` | 진짜 글자 | **65** |

잡음이 진짜 글자보다 높은 신뢰도를 받는다. 임계값을 어디에 두든 진짜 글자를 먼저 잃는다.
그래서 신뢰도 필터는 넣지 않았다. 대신 아래 두 가지를 쓴다.

## 파서

**스탯 이름 화이트리스트를 쓰지 않는다.** 로스트아크 젬 옵션 풀은 패치마다 바뀌고,
나(작성 시점의 Claude)는 현재 게임 내 정확한 툴팁 문구를 확인할 방법이 없다.
확실하지 않은 이름 목록을 하드코딩하면 패치 한 번에 조용히 망가진다.

대신 **형태(shape)** 만 보고 뽑는다. `app.js` 의 `LINE_PATTERNS` 가 전부이고, 위에서부터 첫 매칭을 쓴다.

| 종류 | 매칭 형태 | 예 |
| --- | --- | --- |
| `level` | `... Lv. n` | `공격력 Lv. 1 증가` |
| `point` | `... n 포인트` / `... 포인트 n` | `혼돈 포인트 +3 증가` |
| `percent` | `... n%` | `보스 피해 12.5%` |
| `number` | 줄 끝이 숫자 | `의지력 효율 +1 증가` |

값 뒤의 `증가` / `감소` 접미사를 받아 `delta` 필드에 담는다. 실제 가공 화면의 값이 전부
`Lv. 1 증가`, `+3 증가` 형태라, 이걸 못 받으면 값 줄이 통째로 미매칭으로 빠진다.
`+1` 같은 부호를 잃지 않도록 원문 표기를 `valueText` 에 따로 보존한다.
천 단위 쉼표(`261,267`)도 받는다.

계열은 `질서` / `혼돈` 키워드로만 판별한다(계열 이름은 패치를 타지 않는다).
젬 자체 레벨은 "라벨이 없거나 `젬` 이 들어간 레벨 옵션" 중 첫 번째로 추정한다.
어디에도 안 걸린 줄은 **파싱되지 않은 줄** 에 그대로 보여준다. 이걸 보고 규칙을 늘려가면 된다.

OCR 흔들림 보정(`normalizeOcrText`)도 들어 있다: 전각 -> 반각, `LV`/`lv`/`Ly`/`Lvl`/`Lv3`/`Lv. 3` -> `Lv.3`,
그리고 `L` 이 통째로 날아간 `v2` -> `Lv.2` 까지 되살린다.

> **이 파서는 여전히 베스트 에포트다.** 실제 가공 화면 한 장을 보고 한 차례 고쳤을 뿐,
> 젬 툴팁 자체의 정확한 문구는 아직 확인하지 못했다. `LINE_PATTERNS` 는 계속 튜닝 대상이다.

## 열(컬럼) 재구성

가공 화면 하단은 4개 항목이 **가로로** 늘어서 있고, 각 항목이 "이름 줄 + 값 줄" 2단으로 쌓여 있다.
Tesseract 는 `PSM_SINGLE_BLOCK` 에서 이미지를 위에서 아래로 훑기 때문에 `data.text` 가 이렇게 나온다.

```
의지력 효율   공격력   혼돈 포인트   낙인력
+1 증가   Lv. 1 증가   +3 증가   Lv. 1 증가
```

이름끼리 한 줄, 값끼리 한 줄로 뭉쳐서 **어떤 값이 어떤 항목의 것인지 평문만으로는 복구할 수 없다.**
그래서 단어 위치 정보를 쓴다. tesseract.js 5.1.1 은 `recognize()` 결과에 `data.words[].bbox`
(`{x0,y0,x1,y1}`)를 **기본으로 채워준다** — 별도 `output` 인자는 필요 없다(실측 확인).

`reconstructLines()` 가 하는 일:

1. 단어를 세로 중심 좌표 간격으로 **행**으로 묶는다.
2. 각 행을 가로 간격으로 **셀(열)** 로 쪼갠다.
3. 위아래 두 행이 "이름 행 + 값 행" 이면 셀 단위로 `이름 값` 으로 합친다.
4. 아니면 그 행은 원래대로 한 줄로 흘려보낸다.

3번의 판정 조건이 중요하다. 기하 정보만 보면 `가공 비용 | 900` / `소지 금액 | 261,267` 같은
평범한 2열 표도 "이름 행 + 값 행" 으로 보여서 `가공 비용 소지 금액` / `900 261,267` 로
잘못 묶인다(실제로 처음 구현했을 때 이 버그가 났다). 그래서 의미 조건을 건다:
**위 행 셀에는 숫자가 하나도 없고, 아래 행 셀에는 전부 숫자가 있어야 한다.**

세로로 나열된 일반 툴팁은 각 행이 셀 1개라 3번 조건에 걸리지 않고 자동으로 평문과 같은 결과가 된다.
즉 이 기능은 켜 두어도 기존 동작을 깨지 않는다. 결과 패널의 **인식 방식** 에
`열 재구성` / `행 단위` / `평문` 중 무엇이 쓰였는지 표시되고, **재구성된 줄** 에 중간 결과가 보인다.

조정값은 `app.js` 의 `LAYOUT_DEFAULTS` 에 모여 있고, 전부 "글자 높이의 몇 배" 같은 상대값이라
해상도나 UI 배율이 달라도 그대로 쓸 수 있다.

### 열 경계는 두 행을 함께 보고 정한다

한 행만 보고 가로 간격으로 쪼개면 실제 화면에서 두 열이 통째로 붙어버리는 일이 생긴다.
실측 사례:

```
공격력 +3증가"속 14. 1 증가 A     <- 3번 칸과 4번 칸이 한 셀에 뭉침
```

**원인은 열 간격이 좁아서가 아니다.** 화살표 아이콘이 문자로 깨져 나온 잡음
(`"`, `속`)이 열과 열 사이 빈 공간에 걸터앉아 다리를 놓기 때문이다. 빈 공간이
잡음으로 메워지니 양쪽에 남은 틈이 각각 임계값 밑으로 내려간다.

> 참고로 `cellGapRatio` 는 **확대 배율에 영향받지 않는다.** 간격도 글자 높이도
> 같은 배율로 커지므로 비율은 그대로다. "3.0x 로 올려서 상대적으로 간격이 좁아졌다" 는
> 설명은 성립하지 않는다. 크롭을 좁게 잡는 것도 픽셀 자체는 그대로라 마찬가지다.

임계값을 낮추는 것은 답이 아니다. 낮추면 `의지력 효율` 같은 진짜 라벨이 쪼개진다.
대신 **두 행을 함께 본다.** 진짜 열 경계라면 이름 행에서도 값 행에서도 비어 있어야 한다.
두 행의 빈 구간을 교집합하면, 잡음이 한쪽 행의 복도를 메워도 남은 틈이 경계로 살아남는다.
덤으로 두 행의 칸 개수가 항상 같아져서 짝짓기가 단순한 자리 맞추기가 된다.

측정: 위 사례를 bbox 로 재현했을 때 한 행만 보면 3칸(3/4번 뭉침)으로 쪼개지지만,
교집합 방식은 4칸으로 정확히 분리하고 3번 칸(`의지력효율 +3 증가`)을 복구한다.
4번 칸은 `Lv.` 가 `14.` 로 깨져 있어 복구 불가라 미매칭으로 남는다 - 이게 옳은 동작이다.

교집합이 안 되는 경우(세로형 툴팁 등)에는 기존 방식으로 되돌아가고,
라벨과 값을 짝지을 때는 그리디가 아니라 **순서를 지키는 최소 비용 정렬(DP)** 을 쓴다.
그리디(값마다 제일 가까운 라벨을 집어가기)는 처리 순서에 따라 앞쪽 값이 뒤쪽 값의 라벨을
가로채면 그 뒤가 줄줄이 밀리는 연쇄 오배정이 날 수 있다. 격자 UI 에서 라벨과 값의 순서는
절대 뒤바뀌지 않으므로, 순서를 지키는 최적 정렬을 구하면 처리 순서와 무관하게 항상 같은
결과가 나온다. 칸 수가 한 자리라 비용은 무시할 만하다.

## 잡음을 어디서 막을 것인가

한동안 "정규식을 계속 느슨하게 해서 깨진 줄도 잡아내는" 방향으로 고쳤는데, 그 방향은
막다른 길이었다. 느슨하게 할수록 **장식 배경의 판독 불가 잡음에서 그럴듯한 숫자가 뽑혀
가짜 옵션이 쏟아졌다** (`gemLevel: 437`, 라벨 `" 할게aah 0Bl-...` 값 34,
`가공 완료 가공 하기 (9` 값 9). 재현율을 올리려다 정밀도를 잃은 것이다.

지금은 반대로 간다. **잡음은 파서가 아니라 그 앞 단계에서 막는다.**

### 1. 영역 게이트 (가장 효과가 크다)

가공 화면에는 옵션 격자 바로 위에 `다음 항목 중 무작위로 적용됩니다` 가 있고,
그 아래로는 `가공 비용` / `소지 금액` 이 온다. 이 두 문구 사이만 남기면
상단 원형 장식 영역과 하단 버튼이 통째로 사라진다.

앵커 문구는 짧고 잘 안 깨지는 조각(`무작위`, `적용됩니다`)만 쓴다. 문장 전체를 요구하면
한 글자만 깨져도 못 찾는다. 앵커가 안 보이면(이미 좁게 잘랐거나 젬 툴팁을 보는 중이면)
아무것도 하지 않는다. 결과 패널의 **영역 게이트** 에 몇 행을 걷어냈는지 표시된다.

측정: 장식 배경까지 통째로 넣은 최악의 크롭에서 8행 중 6행이 걸러지고
진짜 옵션 4개만 남았다. 가짜 옵션 0개.

### 2. 라벨의 "한글다움"

이 게임의 옵션 이름은 전부 한글이다. 라벨에서 공백을 뺀 뒤 한글 비율이 60% 미만이면
의심 표시를 단다. `CER EI XA`(0%), `" 할게aah 0Bl-...` 같은 것들이 여기 걸린다.

다만 **의심된다고 바로 버리지는 않는다.** 단위(`Lv`/`포인트`/`%`/`회`)가 맞아떨어졌거나
증감 접미사(`증가`/`감소`)가 붙어 있으면 라벨만 깨졌을 뿐 값은 진짜일 가능성이 높다
(실측 사례: `XA효율 +3 증가` 는 사실 `의지력 효율 +3 증가`). 이런 건 옵션으로 살리고
라벨 옆에 `이름?` 표시만 단다.

단위도 없고 증감도 없는데 라벨까지 잡음인 것 - 가짜 옵션이 쏟아지던 통로가 정확히 여기다 -
만 **의심스러운 항목** 목록으로 따로 뺀다.

### 3. 줄 끝 잡음은 딱 필요한 만큼만

값 오른쪽 상승 화살표가 `A` 나 `초` 로 읽힌다. 줄 끝을 `\s*$` 로 딱 닫으면 이런 줄이
통째로 미매칭되므로 잡음을 허용해야 하는데, 한때 이걸 `[\sA-Za-z"'_().,:▲▼]{0,5}$` 까지
넓혔다가 `가공 완료 가공 하기 (9` 같은 버튼 텍스트가 옵션으로 들어왔다.
실제로 관찰된 잡음은 **짧은 토큰 하나**뿐이라 딱 그만큼만 허용한다.

라벨도 반드시 글자로 끝나야 한다. 예전엔 여는 괄호로 끝나는 라벨
(`가공 완료 가공 하기 (`)이 통과했는데 이게 가짜 옵션의 주요 통로였다.

## 회귀 테스트

실제 게임을 다시 캡처하지 않고 파서 변경을 검증한다.

```bash
node web/gempago-poc/test-fixtures/run-tests.js
```

`test-fixtures/captures.json` 에 실제 화면에서 나온 OCR 결과가 들어 있다.
캡처 하나는 `rawText`(OCR 원문, 평문 경로 검사) 또는 `lines`(열 재구성 이후의 줄,
줄 단위 정규식 검사) 형태로 넣을 수 있다.

**새 캡처를 추가하는 법**: 페이지에서 인식한 뒤 *원본 OCR 텍스트* 칸과
*재구성된 줄* 패널의 내용을 그대로 복사해서 새 항목으로 넣고, 화면을 눈으로 보고
`expect` 를 채운다. `forbid` 에는 "옵션으로 잡히면 안 되는" 조각을 적는다
(가짜 옵션 회귀를 막는 데 이게 제일 유용하다).

## 검증한 것 / 검증 못 한 것

실제 로스트아크를 띄워놓고 확인할 수는 없었다. 다만 **사용자가 실제 가공 화면으로 한 번 돌려본
결과를 전달받아** 그걸 근거로 고친 부분이 있다. 아래는 무엇이 어디까지 확인된 것인지 구분한 것이다.

### 검증됨 (Node 에서 실제로 실행)

- **자동 테스트 121건 전부 통과.** 파서 단위 32 + 격자 분할 13 + 열 재구성/실제 OCR 24 +
  전체 화면 종단 9 + 실전 캡처 회귀 43.
- **열 뭉침 버그를 bbox 로 재현하고 고친 것을 확인.** 재현 상태에서 한 행만 보면
  3칸으로 뭉치지만, 두 행 교집합 방식은 4칸으로 분리하고 3번 칸을 복구한다.
- **최악 조건 종단 테스트.** 장식 배경 + 다이아몬드 + 4열 + 하단 버튼을 전부 포함한
  "넓게 잡은 크롭" 을 새 파이프라인에 통과시켰더니, 8행 중 6행이 영역 게이트에서
  걸러지고 **진짜 옵션 4개만, 가짜 옵션 0개, 미매칭 0개** 로 나왔다.
  값은 `+2 증가` / `1회 증가` / `+3 증가` / `Lv.1 증가` 전부 정확했다.
- **48조합 전처리/PSM 벤치마크.** 위 "확대 배율이 가장 중요하다" 표가 그 결과다.
- **신뢰도 필터가 쓸모없다는 것을 측정으로 확인.** 위 표 참고. 넣지 않기로 한 근거다.
- **OCR 파이프라인 실제 동작 확인.** Pillow 로 합성 이미지를 만들고 `app.js` 의 전처리를
  똑같이 적용한 뒤 진짜 `tesseract.js@5.1.1` 로 돌렸다. 세로형 툴팁 합성 이미지에서
  구조화 필드 **7/7 정확**(계열 `질서`, 젬 레벨 `7`, 옵션 6개).
- **가공 화면의 4열 레이아웃을 합성 이미지로 재현하고, 실제 OCR 로 같은 증상을 그대로 재현했다.**
  `data.text` 가 이름 줄/값 줄로 뭉쳐 나오는 것을 눈으로 확인한 뒤, bbox 기반 열 재구성을 붙여
  **4쌍(`의지력 효율 +1 증가`, `공격력 Lv. 1 증가`, `혼돈 포인트 +3 증가`, `낙인력 Lv. 1 증가`)을
  전부 올바르게 복원**하는 것까지 확인했다.
- **`data.words[].bbox` 가 tesseract.js 5.1.1 에서 기본 제공됨을 실측 확인.**
  `recognize()` 에 별도 `output` 인자를 주지 않아도 `words`(36개) / `lines` / `blocks` 가 모두
  채워져 나왔다. `blocks[].paragraphs[].lines[].words[]` 계층도 같이 확인했다.
- **세로형 툴팁이 열 재구성으로 망가지지 않음을 확인.** 같은 코드에 세로 툴팁 이미지를 넣으면
  `mode: row` 로 떨어지고 결과가 기존과 동일했다.

이 과정에서 실제로 잡은 버그들 (전부 수정 완료):

1. `kor` 단독은 `Lv.` 같은 라틴 문자를 **통째로 흘려버린다.** -> `OCR_LANGS = 'kor+eng'`.
2. 반전을 안 걸면 `12.5%` 가 `125%` 로 깨졌다. -> **밝기 반전 기본 켬.**
3. 게임은 `Lv. 1` 처럼 **점 뒤에 공백**을 넣는데 패턴이 `Lv\.\d` 라 못 잡았다. -> `Lv\.\s*\d`.
4. 가공 화면 값은 `+3 증가` 처럼 **증감 접미사**가 붙어서 값 줄이 전부 미매칭이었다. -> `delta` 지원.
5. 기하 정보만으로 행을 짝지으면 `가공 비용 | 900` / `소지 금액 | 261,267` 이
   `가공 비용 소지 금액` 으로 **잘못 병합**됐다. -> "위 행엔 숫자 없음 + 아래 행엔 전부 숫자" 조건 추가.
6. Tesseract 가 한글을 글자 단위로 쪼개서(`의`,`지`,`력`) 공백으로 이으면 `의 지 력` 이 됐다.
   -> 단어 간격이 실제로 벌어진 곳에만 공백을 넣도록 수정.
7. `261,267` 의 **천 단위 쉼표** 때문에 `소지 금액 261,` + `267` 로 잘렸다. -> 쉼표 허용.

### 검증 안 됨 (직접 확인 필요)

- **실제 가공 화면에서 이번 수정이 통하는지.** 벤치마크는 실제 화면을 흉내낸 합성
  이미지다. 진짜 화면의 장식 배경은 이보다 훨씬 지저분하다(합성본은 장식 영역에서
  단어 6개만 나왔지만 실제로는 판독 불가 조각이 훨씬 많이 나왔다).
  **확대 배율 3.0x 로 다시 한 번 돌려보는 것이 이번 라운드의 핵심 확인 사항이다.**
- **`Lv.` 가 깨지면 그 칸은 못 살린다.** 캡처마다 `1.`, `14.`, `v` 등으로 다르게 깨진다.
  이건 문자 단위 오독이라 정규식으로 복구할 수 없고, 억지로 숫자를 뽑아내면
  **틀린 값을 맞다고 보여주게 되므로** 미매칭으로 남기는 쪽을 택했다.
  값이 필요하면 확대 배율을 더 올리거나(4.0x) PSM 을 바꿔보는 것이 유일한 대응이다.
  드물게 깨진 조각이 서로 붙어 `14.1` 같은 그럴듯한 숫자가 될 수 있는데, 이때는
  값이 조용히 틀릴 수 있다. **재구성된 줄 패널을 같이 보는 것을 권장한다.**
- **라벨 앞에 아이콘이 글자로 붙는 문제는 안 고쳤다.** 작은 아이콘이 `티` 같은
  한 글자로 읽혀서 `티 의지력 효율` 처럼 나온다. 값에는 영향이 없다.
  "앞의 한 글자를 떼는" 규칙을 넣으면 `의 지력 효율` 처럼 진짜 라벨이 쪼개진 경우에
  진짜 글자를 지워버릴 수 있어서, 값의 정확도를 지키는 쪽을 택했다.
- **상단 원형 장식 영역은 손대지 않았다.** 기요셰(guilloche) 무늬 배경 위에 입체 음각 글씨라
  OCR 이 거의 전부 깨진다(`SS ENP`, `df PSL` 같은 결과). 이건 별개의 훨씬 어려운 문제라
  이번에는 의도적으로 제외했다. 쓸모 있는 데이터는 아래쪽 평평한 배경의 4열 행이다.
  **선택 영역을 아래쪽 행에만 맞추는 것을 권장한다.** 장식 영역이 들어가면 쓰레기 줄만 늘어난다.
- **젬 툴팁 자체의 정확한 문구.** 이번에 확인한 것은 가공 화면이지 젬 툴팁이 아니다.
  `LINE_PATTERNS` 가 진짜 툴팁 옵션 줄을 다 잡는지는 여전히 모른다.
- **브라우저에서의 실제 동작.** `getDisplayMedia`, 사각형 드래그/리사이즈, 캔버스 크롭 좌표 계산은
  브라우저 없이 실행해볼 수 없었다. HTML 의 id 와 JS 참조가 1:1로 맞는 것까지만 기계적으로 확인했다.
- 합성 이미지에서도 `질서의 젬` 의 `젬` 한 글자는 계속 틀렸다(`A`, `d` 등).
  계열 판별은 `질서` 로 하니 결과에는 영향이 없었지만, 짧은 단어는 원래 잘 틀린다는 신호다.
- 라벨 안의 **띄어쓰기 위치는 완벽하지 않다** (`의지 력 효율` 처럼 나올 수 있다).
  간격 임계값(`wordGapRatio`)에 달린 문제인데, 숫자 파싱에는 영향이 없어서 우선순위를 낮게 뒀다.

## 알려진 거친 부분

- **첫 로딩이 느리다.** `kor+eng` 학습 데이터를 CDN 에서 받는다. 합쳐서 대략 15~20MB,
  회선에 따라 수십 초. 한 번 받으면 브라우저(IndexedDB)에 캐시되어 다음부터는 빠르다.
- **`file://` 로는 안 된다.** 위 실행 방법대로 로컬 서버를 띄워야 한다.
- **전체 화면 게임은 캡처가 안 될 수 있다.** 테두리 없는 창 모드를 쓰자.
- **자동 인식 2초는 실제로는 더 느릴 수 있다.** 한 번 인식에 걸리는 시간이 2초를 넘으면
  다음 타이머는 그냥 건너뛴다(중복 실행 방지). 영역이 클수록 느려진다.
- 인식은 메인 스레드에서 워커를 호출하는 방식이라, 큰 영역을 자동 인식으로 돌리면 UI 가 살짝 버벅일 수 있다.
- 선택 영역은 새로고침하면 초기화된다(저장 안 함).
- OCR 보정 규칙 중 `v2 -> Lv.2` 는 한글 툴팁을 전제로 한 휴리스틱이다.
  로마 숫자 `V` 를 쓰는 문구가 있다면 `app.js` 의 해당 줄을 지워야 한다.
- **장식 배경 위의 글씨는 사실상 못 읽는다.** 가공 화면 상단의 원형 무늬 + 입체 음각 글씨가 그렇다.
  선택 영역을 평평한 배경 쪽으로 잡는 것이 유일한 실용적 회피책이다.
- 열 재구성은 "이름 행 바로 아래 값 행" 이라는 2단 구조만 처리한다.
  3단 이상이거나 항목마다 줄 수가 다르면 짝이 맞지 않아 평문 처리로 떨어진다.

## 파서만 따로 테스트하기

`app.js` 는 파서 부분을 Node 에서 쓸 수 있게 export 한다 (브라우저에서는 무시됨).

```bash
node -e "const p=require('./web/gempago-poc/app.js'); console.log(JSON.stringify(p.parseGemTooltip(p.SAMPLE_TEXT),null,2))"
```

페이지 안에서도 **샘플 텍스트로 파서 테스트** 버튼으로 OCR 없이 파서만 돌려볼 수 있다.
